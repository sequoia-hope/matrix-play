PCB Design

The goal is a board a senior engineer would sign off on: a schematic that reads like a person drew it, a layout that follows the physics, every part checked against its datasheet, and a project page that shows the user what is happening at all times.

The work runs in phases. Each phase ends at a gate: a file in design/gates/ containing the checklist for that phase, the evidence for each item (command output, calculation, render), and the reviewer's findings. A phase is not done until its gate file exists and an independent reviewer has signed it off. Saying "done" without a gate file is a failure.

Before anything else

  1. Read LESSONS.md in this skill folder. These are corrections the user has already had to give. Repeating one is the worst kind of mistake.
  2. Find out which tool this project uses and read tools/kicad.md or tools/altium.md.
  3. Check whether the project is open source (personal boards, KiCad, GitHub repo link on silkscreen, public PCB view) or work/confidential (Altium, internal part number, no public repo or page). This changes silkscreen, publishing and what may leave the machine.
  4. Run scripts/doctor.sh once per machine; fix anything it reports before phase 2.
  5. Look for an existing design/ folder and gate files and resume from the last passed gate rather than starting over.

At every gate

  1. Run the checks for the phase. Paste the actual output into the gate file. Never write "passed" for a check you did not run.
  2. Export renders (schematic PDF, per-layer copper, top/bottom with silk, 3D) for anything visual: scripts/render.py <hw dir> design/renders. Look at them yourself before the reviewer does.
  3. Spawn an independent reviewer (see "Model routing" below) with only the artifacts and the checklist.
  4. Fix findings, or dispute them in decisions.md with reasoning. Re-review if anything significant changed.
  5. Update design/status.json and regenerate the viewer (scripts/view.sh build pcbview.toml) so the user can see the new state from their phone.
  6. If the phase needs user sign-off, stop and say exactly what you need them to decide.

Iterating

Going backward is normal. When an upstream artifact changes (a part swap, a new net, a moved connector), list which downstream gates it invalidates, mark them stale in their gate files, and re-run them. Never patch downstream to hide an upstream change.

Experiments get their own variant: a new folder under hw/<board>/, a [[boards]] entry in pcbview.toml naming its parent and what changed, and its own gates from the point it diverged. Never overwrite a variant the user has looked at.

Hard rules

  • Schematic is the only source of truth for values, footprints, MPNs and supplier part numbers. Never edit these in the PCB. Change the schematic, push to the PCB, run the sync check.
  • No part without its datasheet opened. If a datasheet can't be fetched, stop and ask the user to attach it. Never fill in a part's requirements from memory.
  • No programmatic-looking schematics. No grids of symbols, no global labels standing in for wires within a sheet, no blocks of passives detached from what they serve. See references/schematic-style.md.
  • No passives in a row. Every passive sits with the part it serves. See references/placement.md.
  • Don't hand-route long traces by coordinates. Power goes in pours and planes, critical nets are kept short by placement, and everything else goes to the autorouter with full net-class rules.
  • Via counts come from calculation, never a single via on a net whose current needs more.
  • Never suppress or waive a DRC/ERC error silently. Every waiver goes in decisions.md with a reason.
  • Zero silkscreen overlaps. Fix colliding footprint silk with a board-local footprint edit.
  • Never edit pcbview inside a project (vendor/pcbview is a pinned submodule). File a change request instead (see references/pcbview.md).
  • Log every non-obvious decision in decisions.md as it happens, not afterward.

Model routing

Use the main session model (e.g. Opus) for generation: writing files, running tools, scripts, bulk edits.

Use a stronger model (e.g. Fable) as a fresh-context subagent for judgment:

  • datasheet cross-check: independently re-read the datasheet and recompute every calculation
  • schematic visual review: does this read like a human drew it?
  • placement and silkscreen review on renders
  • SI/EMC judgment: what could couple into what, and what needs simulating
  • final release review

The reviewer gets the artifacts, the relevant reference checklist and nothing else: not the conversation, not the author's reasoning. It returns findings ranked by severity. See references/review-protocol.md for prompts.

When the user corrects you

Add the correction to LESSONS.md as a concrete rule (what was wrong, what to do instead) in the same turn. The skill should get better every time it is corrected.
